# zenoh_flutter

A Flutter app for watching live Zenoh data on a phone. It opens a Zenoh session as a peer, client or router, and lists every key expression it receives on a discovery scope. For one key at a time, it shows the newest sample as formatted JSON, text, an image or a hex dump. It talks to Zenoh through the local FFI package [`packages/zenoh_dart`](packages/zenoh_dart/README.md), and it bundles `zenoh-c` built for Android and iOS. It is also the swarmbotix `sb` module `zenoh_flutter`: its subscribers to the `pubsub_flutter` test publisher and to the ws-ips image relay are generated by `sb io`, and it decodes ROS2-style messages from the sb message vault, drawing compressed (JPEG, PNG) and raw-pixel camera images (see [swarmbotix (sb) module](#swarmbotix-sb-module)).

## Screens

- **Session** (`/settings`, the start screen): pick the mode, its endpoints and the discovery scope, then open the session. A status line and a session log show what happened. When you press the button, the settings are saved on the device (`shared_preferences`, key `session_settings_v1`). The app always starts on the **peer** tab, which opens a session even when no router is found; the saved fields of every mode are restored when you switch to it.
- **Topics** (`/topics`): every key expression seen on the discovery scope (default `**`), with its payload type, last size and publish rate. A row dims after 10 s without data and disappears after 60 s. You can also subscribe to any key expression by hand.
- **Viewer** (`/view`, with the key expression passed as the route argument): one card updated in place, the PUB HZ, DRAW HZ and LAST meters, a pause button, and long-press to copy the payload. Protobuf and FlatBuffers samples whose encoding names a known message (`application/protobuf;ros2/sensor_msgs/Imu`) are decoded and shown as JSON, and an image inside a protobuf message is drawn under it: the JPEG in a `sensor_msgs/CompressedImage`, or the raw pixels of a `sensor_msgs/Image` (see [Raw images](#raw-images)).
- **swarmbotix io** (`/sbio`, no button in the UI at the moment; reachable by route only): opens the eleven subscribers that `sb io` generated for this module on the app's session and shows one live card per topic, with the same meters and payload card as the Viewer. Tap a topic's title to open it in the Viewer. The subscribers close when you leave the screen or the session drops.

[docs/APP_GUIDE.md](docs/APP_GUIDE.md) explains every control and has a troubleshooting list.

## Zenoh modes

| Mode | What the app configures | Use it when |
|---|---|---|
| **peer** (default) | Multicast scouting on. Under **Advanced**: an optional address to connect to, plus tcp and udp listeners on any free port and a ws listener on 8000 | Devices on one LAN should find each other |
| **client** | One address to connect to. No listeners, scouting off | You know the router's address |
| **router** | tcp 7447 and udp 7447 listeners (ws 8000 optional), scouting off by default, optional other routers to connect to | The phone itself should be the hub |

Multicast scouting does not work on the Android emulator, or on iOS without the multicast entitlement. On those devices, give the app an explicit address: use client mode, or peer mode with **Advanced** > **Connect to (optional)**. The emulator reaches the host computer at `10.0.2.2`. On Android, client mode starts with `tcp/10.0.2.2:7447`; on other platforms it starts with `127.0.0.1`. See [docs/MULTICAST.md](docs/MULTICAST.md).

## Native Zenoh libraries

The app bundles prebuilt `zenoh-c` binaries. Each version is built into `packages/zenoh_dart/native/<platform>/<version>/` with the build script for its platform:

```bash
bash .claude/skills/zenoh-build-android/build_zenoh_android.sh <version>      # Linux or macOS: Rust, cargo-ndk and the Android NDK
bash .claude/skills/zenoh-build-ios/build_zenoh_ios.sh <version>          # macOS with Xcode only
```

Then one version is activated for the app with the `zenoh-activate-libs` skill script:

```bash
bash .claude/skills/zenoh-activate-libs/copy_zenoh_libs.sh <version>          # Android (default)
bash .claude/skills/zenoh-activate-libs/copy_zenoh_libs.sh <version> ios      # iOS
bash .claude/skills/zenoh-activate-libs/copy_zenoh_libs.sh <version> all      # both
```

Platform-specific build instructions:

- [docs/BUILD_ANDROID.md](docs/BUILD_ANDROID.md) – build `libzenohc.so` with `bash .claude/skills/zenoh-build-android/build_zenoh_android.sh <version>`, or by hand with `cargo ndk` (Linux or macOS), and copy it into `android/app/src/main/jniLibs/`.
- [docs/BUILD_IOS.md](docs/BUILD_IOS.md) – build `zenohc.xcframework` with `bash .claude/skills/zenoh-build-ios/build_zenoh_ios.sh <version>` (macOS + Xcode only) and vendor it through `packages/zenoh_dart/ios/zenoh_dart.podspec`.
- [docs/MULTICAST.md](docs/MULTICAST.md) – why multicast scouting is blocked on the Android emulator and on iOS, how to get the iOS multicast entitlement, and what to do instead.

## Running

```bash
flutter pub get
flutter run -d <device>
```

### Android emulator

```bash
flutter emulators                                   # list available emulators
flutter emulators --launch Medium_Phone_API_36.1    # start it (boots in ~10 s)
flutter devices                                     # wait until "emulator-5554" shows up
flutter run -d emulator-5554                        # build and run the app on it
```

Inside the emulator, `10.0.2.2` is the host machine. The app starts in peer mode, and scouting finds nothing in the emulator. Stay in peer mode and enter `10.0.2.2` (tcp, 7447) under **Advanced** > **Connect to (optional)**: the app then joins the mesh through a router running on the same computer. Client mode with its default `tcp/10.0.2.2:7447` reaches the same router.

### Router

In peer mode on a LAN where multicast works, the app finds other peers without a router. Otherwise (the Android emulator, iOS without the multicast entitlement, client mode), a Zenoh router must be reachable from the device, unless the phone runs in router mode itself. The router runs standalone, outside this repo (for example in a container from the `eclipse/zenoh` image), and listens on `tcp/7447`, `udp/7447` and `ws/8000`. On a physical phone, enter the LAN address of the router's computer.

### Test data

The test publisher is the sb module `pubsub_flutter` in the ws-icp repo. From the root of that repo:

```bash
pip install -r pubsub_flutter/requirements.txt   # once: eclipse-zenoh, protobuf>=7.35, flatbuffers, pillow
python3 pubsub_flutter/main.py                   # Ctrl-C to stop
```

It needs the sb message vault compiled (proto for its types, fb for `ros2/sensor_msgs/Temperature`). It opens a zenoh peer session and publishes nine keys, each through a publisher that `sb io` generated. Every sample carries sb's wire tag as its zenoh encoding, `application/protobuf;<vault type>` or `application/flatbuffers;<vault type>`:

| Key | Message | Rate | Encoding |
|---|---|---|---|
| `elcom/ws_icp/pubsub_flutter/zenoh/imu` | `ros2/sensor_msgs/Imu` | 50 Hz | `application/protobuf;ros2/sensor_msgs/Imu` |
| `elcom/ws_icp/pubsub_flutter/zenoh/temperature` | `ros2/sensor_msgs/Temperature` | 50 Hz | `application/flatbuffers;ros2/sensor_msgs/Temperature` |
| `elcom/ws_icp/pubsub_flutter/zenoh/chatter` | `ros2/std_msgs/String` | 2 Hz | `application/protobuf;ros2/std_msgs/String` |
| `elcom/ws_icp/pubsub_flutter/zenoh/cam` | `ros2/sensor_msgs/CompressedImage` | 30 Hz | `application/protobuf;ros2/sensor_msgs/CompressedImage` |
| `elcom/ws_icp/pubsub_flutter/zenoh/raw` | `ros2/std_msgs/UInt8MultiArray` | 5 Hz | `application/protobuf;ros2/std_msgs/UInt8MultiArray` |
| `elcom/ws_icp/pubsub_flutter/zenoh/markers` | `ros2/custom/MarkerDetections` | 20 Hz | `application/protobuf;ros2/custom/MarkerDetections` |
| `elcom/ws_icp/pubsub_flutter/zenoh/cube_poses` | `ros2/custom/CubePoses` | 20 Hz | `application/protobuf;ros2/custom/CubePoses` |
| `elcom/ws_icp/pubsub_flutter/zenoh/image` | `ros2/sensor_msgs/Image` | 10 Hz | `application/protobuf;ros2/sensor_msgs/Image` |
| `elcom/ws_icp/pubsub_flutter/zenoh/debug_image` | `ros2/sensor_msgs/Image` | 10 Hz | `application/protobuf;ros2/sensor_msgs/Image` |

`cam` holds a 320x240 JPEG in `data` (format `jpeg`), which the card draws. `image` and `debug_image` hold uncompressed 640x512 frames, `mono8` and `rgb8`, which the card converts and draws. `raw` holds 256 bytes, `chatter` a line of text in a `std_msgs/String`. The Viewer picks the decoder from the vault type after the semicolon, and the Topics list shows `protobuf` or `flatbuffers` from the part before it. The **swarmbotix io** screen decodes each of its keys with the type in `sb.module.yaml`.

`markers` and `cube_poses` carry the types of the ws-ips marker pipeline (`custom/MarkerDetections.proto` and `custom/CubePoses.proto` in the vault, protobuf package `swarmbotix.custom`). The ws-ips modules publish the same types with the same wire tags on `elcom/ws_ips/ips_detect-sbNN/zenoh/markers` (one key per detector instance, for example `ips_detect-sb00`) and `elcom/ws_ips/ips_track/zenoh/cube_poses`. The swarmbotix io screen does not subscribe to those keys, but Topics lists them when the scope covers them (the default `**` does) and the Viewer decodes them like any other known type.

The ws-ips image relay `ips_image_relay` (one instance per robot, `sb00` to `sb03`) publishes `ros2/sensor_msgs/Image` with the same wire tag on `elcom/ws_ips/ips_image_relay-sbNN/zenoh/image` (`mono8`) and `elcom/ws_ips/ips_image_relay-sbNN/zenoh/debug_image` (`rgb8`). The swarmbotix io screen subscribes to the two keys of `sb00` (`relay_image` and `relay_debug_image`); their cards show the waiting state until the relay runs. `sb01` to `sb03` have no sb entries: open them from Topics, and the Viewer draws them like any `sensor_msgs/Image`.

### Raw images

A `ros2/sensor_msgs/Image` carries raw pixels rather than a JPEG or PNG: `width`, `height`, `encoding`, `is_bigendian`, `step` (bytes per row) and `data` (`step * height` bytes). The card shows its fields as JSON (with `data` as `<N bytes>`), a `<width>x<height> <encoding>` chip, and the image under them. The app converts each frame to RGBA in the background and draws the result; only the newest frame is converted when frames arrive faster than that, and older ones are dropped. Supported encodings:

| `encoding` | Drawn as |
|---|---|
| `mono8` | grey |
| `rgb8`, `bgr8` | colour |
| `rgba8`, `bgra8` | colour; alpha is ignored (drawn opaque), as `rqt_image_view` does |
| `mono16` | grey, best effort: each frame is stretched from its darkest to its brightest pixel; `is_bigendian` picks the byte order |

Row padding (a `step` larger than `width` times the bytes per pixel) is skipped. A frame that cannot be drawn (another encoding, a zero size, a `step` shorter than a row, or `data` shorter than `step * height`) shows its JSON and a red `cannot draw image: …` line saying why. The code is `lib/topics/raw_image.dart`.

On a phone on the same LAN as the computer, the app in peer mode finds the publisher by multicast scouting; no router is needed. On the Android emulator, run a zenoh router on the computer (for example `docker compose up -d` in the ws-icp repo root, which listens on tcp/udp 7447 and ws 8000), keep the app in peer mode with **Advanced** > **Connect to (optional)** set to `10.0.2.2`, and let the publisher reach the same router: it finds it by scouting on the computer, or `python3 pubsub_flutter/main.py --connect tcp/127.0.0.1:7447` points it there directly.

## swarmbotix (sb) module

The repo root is the sb module `zenoh_flutter` (language `flutter`). It was adopted with `sb init . --flutter`, which registered it in the active workspace `ws_icp` (`~/.swarmbotix/workspaces/ws_icp/sb.workspace.yaml`); the repo has no `sb.workspace.yaml` of its own.

- **`sb.module.yaml`** lists the eleven subscribers: `imu`, `temperature`, `chatter`, `cam`, `raw`, `markers`, `cube_poses`, `image` and `debug_image` for the test publisher, and `relay_image` and `relay_debug_image` for the ws-ips image relay (instance `sb00`). Each is a `key:` entry with the publisher's full wire key, added with `sb io add sub --key elcom/ws_icp/pubsub_flutter/zenoh/<name> -m <vault type> --zenoh -n <name>` (plus `--fb` for `temperature`), or for the relay `sb io add sub --key elcom/ws_ips/ips_image_relay-sb00/zenoh/<image|debug_image> -m ros2/sensor_msgs/Image --zenoh -n relay_<image|debug_image>`. Because the keys are verbatim, the active sb workspace does not change them. `io_dir` is `lib/swarmbotix_io` rather than sb's default `swarmbotix_io`, because Dart can import a file by `package:` URI only from `lib/`. `sb io list` shows the entries.
- **`lib/swarmbotix_io/subscribers/<name>.dart`** are generated by sb: one `<Name>Subscriber` per entry, with `open(session)`, `tryRecvLatest()` (the newest payload since the last call, as bytes) and `close()`. Never edit them. Regenerate them with `sb io update` in the repo root after changing `sb.module.yaml`, the `device:` in `~/.swarmbotix/sb.config.yml` or the workspace. After `sb io add sub`, add the new entry to `lib/topics/sbio_topics.dart` so the swarmbotix io screen shows it.
- **`lib/zenoh_flutter.dart`** exists for sb's Flutter template. The generated files import `package:zenoh_flutter/zenoh_flutter.dart` and use `Session.declareSubscriber(keyExpr, (Sample sample) {...})`, `Sample.payload` and `Subscriber.undeclare()` (generated publishers use `Session.declarePublisher`, `Publisher.put` and `Publisher.undeclare`, and the examples in their comments use `Zenoh.open()`). This file implements that API over `packages/zenoh_dart`. `Session.fromClient` wraps the session the app already has open, so the generated subscribers run in the app's peer session.
- **Message bindings.** sb's proto backend emits no Dart, so `bash tools/gen_ros2_messages.sh` generates them from the vault (`<messages_root>/ros2/message_definitions`): `protoc --dart_out` for the protobuf types and their imports into `lib/proto/ros2/` (`lib/proto/ros2/<vault dir>/<Leaf>.pb.dart`, so the `swarmbotix.custom` messages land in `custom/`), and for `ros2/sensor_msgs/Temperature` `flatc --proto` then `flatc --dart` into `lib/fbs/ros2/`, the same conversion `sb message compile --fb` uses. The script checks the FlatBuffers schema against sb's compiled `.bfbs`, so the layout matches the Python publisher's. It reads `protoc`, `flatc` and `messages_root` from `~/.swarmbotix/sb.config.yml`, and needs `dart pub global activate protoc_plugin` once. All outputs are committed; run it only after the message list or the vault changes.
- sb's Flutter template is bytes-only: the generated subscribers drop the sample's encoding. The swarmbotix io screen therefore decodes each payload with the wire tag sb stamps for the entry's type and encoding, and shows the encoding that actually arrived under each card.

## Project layout

- `lib/main.dart` – app entry point, routes and theme.
- `lib/fbs/ros2/` – generated Dart FlatBuffers bindings for `ros2/sensor_msgs/Temperature` and its imports, from the sb vault. Do not edit them; run `bash tools/gen_ros2_messages.sh` instead.
- `lib/pages/` – the Session, Topics, Viewer and swarmbotix io screens.
- `lib/proto/ros2/` – generated Dart protobuf bindings for `sensor_msgs/Imu`, `sensor_msgs/CompressedImage`, `sensor_msgs/Image`, `std_msgs/String`, `std_msgs/UInt8MultiArray`, `custom/MarkerDetections`, `custom/CubePoses` and their imports, from the sb vault. Do not edit them; run `bash tools/gen_ros2_messages.sh` instead.
- `lib/session/` – session settings (load, save, validation, conversion to `ZenohConfig`), the app-wide session controller and its log.
- `lib/swarmbotix_io/` – the subscribers `sb io` generates from `sb.module.yaml`. Do not edit them; run `sb io update` instead.
- `lib/topics/` – topic discovery, payload type detection, the protobuf and FlatBuffers decoders (keyed by vault type), raw-image conversion (`raw_image.dart`), the table of sb io topics, the 1 s rate counter and display formatting.
- `lib/zenoh_flutter.dart` – the `package:zenoh_flutter/zenoh_flutter.dart` API that sb's Flutter templates import, implemented over `packages/zenoh_dart`.
- `lib/widgets/` – connection strip, endpoint and listen-row editors, payload card, rate meter, session log sheet.
- `packages/zenoh_dart/` – the FFI package: Dart API, generated bindings, versioned native binaries and the iOS podspec. See [its README](packages/zenoh_dart/README.md).
- `docs/` – app guide, Android and iOS build guides, multicast notes.
- `tools/` – `gen_ros2_messages.sh`, which regenerates `lib/proto/ros2/` and `lib/fbs/ros2/` from the sb message vault.
- `sb.module.yaml` – the sb module manifest: module name, language, `io_dir` and the eleven subscribers.
- `.claude/skills/` – Claude Code skills `zenoh-build-android`, `zenoh-build-ios` and `zenoh-activate-libs`, each holding its script. Claude Code picks them up automatically in this repo; run the scripts directly with `bash .claude/skills/<skill>/<script> <version>`.
